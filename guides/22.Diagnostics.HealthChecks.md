# 22. Діагностика та Health Checks (22.Diagnostics.HealthChecks)

## Призначення та огляд

У сучасній мікросервісній розробці та контейнеризованих середовищах (Kubernetes, Docker Swarm, Nomad, Azure Container Apps) оркестратор повинен постійно знати технічний стан кожного інстансу застосунку.

Платформа ASP.NET Core надає потужну вбудовану підсистему **Health Checks**:
1. **Liveness Probe (`/health/live`)**: відповідає на питання «Чи живий процес?». Застосовується для виявлення зависань (deadlock) та аварійного перезавантаження контейнера.
2. **Readiness Probe (`/health/ready`)**: відповідає на питання «Чи готовий застосунок приймати користувацький трафік?». Перевіряє доступність критичних залежностей (БД, кеш, зовнішні API).
3. **Структурований JSON-звіт**: надання повної картини стану компонентів, тривалості кожної перевірки та додаткових діагностичних даних.

---

## Чому розділення на Liveness та Readiness є критичним?

Уявіть ситуацію: тимчасово впала база даних Postgres або сервіс авторизації.
- **Якщо у вас лише одна загальна перевірка Liveness:** Kubernetes побачить, що перевірка падає, і почне **циклічно вбивати і перезапускати ваші контейнери** (CrashLoopBackOff). Це лише погіршить ситуацію, збільшить навантаження на процесор і зробить неможливим логування помилок.
- **Коли проби розділені:**
  - Liveness залишається **зеленим** (процес не вбивають).
  - Readiness стає **червоним** (балансувальник трафіку просто тимчасово знімає трафік із цього інстансу до відновлення зв'язку з БД).

## Розбір коду

### 1. Кастомний HealthCheck (`CatalogHealthCheck.cs`)
```csharp
public sealed class CatalogHealthCheck(ICatalog catalog) : IHealthCheck
{
    public static bool IsDegraded { get; set; }
    public static bool IsFailing { get; set; }

    public Task<HealthCheckResult> CheckHealthAsync(HealthCheckContext context, CancellationToken ct = default)
    {
        if (IsFailing)
            return Task.FromResult(HealthCheckResult.Unhealthy("Сховище недоступне (симуляція аварії)."));

        if (IsDegraded)
            return Task.FromResult(HealthCheckResult.Degraded("Сховище відповідає з підвищеною затримкою."));

        var count = catalog.GetProducts().Count;
        return Task.FromResult(HealthCheckResult.Healthy(
            description: $"Сховище готове до роботи, доступно {count} товарів.",
            data: new Dictionary<string, object> { ["productCount"] = count }));
    }
}
```

### 2. Реєстрація та тегування перевірок
```csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddCheck<CatalogHealthCheck>("catalog_storage", tags: ["ready"]);
```

### 3. Маршрутизація та фільтрація через предикат
```csharp
// Тільки тег "live": перевіряється виключно працездатність самого процесу
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live"),
    ResponseWriter = WriteJsonResponse
});

// Тільки тег "ready": перевіряються зовнішні залежності
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready"),
    ResponseWriter = WriteJsonResponse
});
```

## Як запустити і перевірити

### Запуск проєкту
```bash
dotnet run --project src/22.Diagnostics.HealthChecks
```
Порт: `5022`.

### Тестові сценарії

1. **Нормальний стан (усі проби зелені):**
   ```http
   GET http://localhost:5022/health/ready
   ```
   cURL:
   ```bash
   curl -s http://localhost:5022/health/ready
   ```
   Повертає `200 OK` зі статусом `Healthy` та детальним списком перевірок:
   ```json
   {
     "status": "Healthy",
     "totalDurationMs": 1.2,
     "checks": [
       {
         "name": "catalog_storage",
         "status": "Healthy",
         "description": "Сховище готове до роботи, доступно 3 товарів."
       }
     ]
   }
   ```

2. **Симуляція аварії сховища даних:**
   ```http
   POST http://localhost:5022/simulate/fail
   ```
   cURL:
   ```bash
   curl -s -X POST http://localhost:5022/simulate/fail
   ```

3. **Перевірка готовності після збою:**
   ```http
   GET http://localhost:5022/health/ready
   ```
   cURL:
   ```bash
   curl -s -i http://localhost:5022/health/ready
   ```
   Сервер повертає **`503 Service Unavailable`** зі статусом `Unhealthy`. Балансувальник Kubernetes припинить маршрутизацію нових клієнтів сюди.

4. **Перевірка Liveness (живучості):**
   ```http
   GET http://localhost:5022/health/live
   ```
   cURL:
   ```bash
   curl -s -i http://localhost:5022/health/live
   ```
   Сервер повертає **`200 OK`**! Процес живий, перезапускати под не потрібно.

5. **Відновлення працездатності:**
   ```http
   POST http://localhost:5022/simulate/restore
   ```
   cURL:
   ```bash
   curl -s -X POST http://localhost:5022/simulate/restore
   ```
   Readiness миттєво повертається до `200 OK`.

## Питання для самоперевірки та співбесіди

1. **Які три основні типи проб використовує Kubernetes і для чого вони потрібні?**
   *Відповідь:*
   - **Startup Probe:** дає повільним застосункам час ініціалізуватися без передчасного перезапуску.
   - **Liveness Probe:** перевіряє, чи не завис процес (deadlock). Якщо проба падає — контейнер вбивається і перезапускається.
   - **Readiness Probe:** перевіряє, чи готовий контейнер приймати трафік. Якщо проба падає — контейнер тимчасово виключається з сервісу/балансувальника, але не вбивається.
2. **Чому не можна додавати важку перевірку бази даних до Liveness Probe?**
   *Відповідь:* Якщо база даних тимчасово недоступна або перевантажена, Liveness проба впаде на всіх подах одночасно. Kubernetes почне перезапускати всі поди сервісу одночасно (каскадна аварія, CrashLoopBackOff), що лише погіршить проблему.
3. **Як організувати різні набори перевірок у межах одного застосунку?**
   *Відповідь:* За допомогою тегів (`tags: ["live"]`, `tags: ["ready"]`) та налаштування фільтра `Predicate = check => check.Tags.Contains(...)` у методах `app.MapHealthChecks(...)`.

## Підсумки
- Вбудована система Health Checks в ASP.NET Core відповідає всім стандартам хмарної оркестрації.
- Тегування (`tags`) дозволяє гнучко налаштовувати незалежні точки діагностики для різних інструментів моніторингу (Prometheus, Kubernetes, Pingdom).
