# 11. Прив'язка та валідація у Minimal APIs (11.MinimalApi.BindingAndValidation)

## Призначення та огляд

Цей приклад демонструє, як у парадигмі **Minimal APIs** у .NET 10 працює прив'язка вхідних параметрів і як вирішується питання перевірки валідності даних.

Головна відмінність від MVC полягає в тому, що в Minimal APIs **немає магії `[ApiController]`**, яка автоматично зупиняє виконання при порушенні `DataAnnotations`. У цьому розділі ми вивчаємо:
1. Джерела прив'язки в Minimal APIs (`[FromRoute]`, `[FromQuery]`, `[FromHeader]`);
2. Зручний патерн об'єднання параметрів у DTO через `[AsParameters]`;
3. **Endpoint Filters (`IEndpointFilter`)** як чистий архітектурний спосіб реалізації автоматичної валідації вхідних моделей.

---

## Патерн `[AsParameters]`

Замість того, щоб перевантажувати сигнатуру методу довгим списком аргументів:
```csharp
// Громіздко:
app.MapGet("/search/{page:int}", (int page, string? term, int pageSize, ICatalog catalog) => ...);
```
Ми оголошуємо єдину структуру (record) і помічаємо її атрибутом `[AsParameters]`:
```csharp
public record SearchParams(
    [FromRoute] int Page,
    [FromQuery] string? Term,
    [FromQuery] int PageSize = 20);

// Лаконічно:
bindGroup.MapGet("/search/{page:int}", ([AsParameters] SearchParams search) =>
    TypedResults.Ok(new { page = search.Page, term = search.Term, pageSize = search.PageSize }));
```
Фреймворк автоматично розбирає маршрут, query string, заголовки та сервіси і заповнює цей об'єкт.

## Валідація через Endpoint Filters

Оскільки Minimal APIs не перевіряють `DataAnnotations` за замовчуванням, найкращим інженерним рішенням у .NET є написання повторно використовуваного **Endpoint Filter**:

```csharp
public sealed class ValidationFilter<T> : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(EndpointFilterInvocationContext context, EndpointFilterDelegate next)
    {
        var argument = context.Arguments.OfType<T>().FirstOrDefault();
        if (argument is not null)
        {
            var validationContext = new ValidationContext(argument);
            var results = new List<ValidationResult>();

            // Запуск валідації DataAnnotations
            if (!Validator.TryValidateObject(argument, validationContext, results, validateAllProperties: true))
            {
                var errors = results
                    .GroupBy(r => r.MemberNames.FirstOrDefault() ?? string.Empty)
                    .ToDictionary(
                        g => g.Key,
                        g => g.Select(r => r.ErrorMessage ?? "Невалідне значення").ToArray());

                // Коротке замикання: повертаємо 400 без входу в тіло хендлера!
                return TypedResults.ValidationProblem(errors);
            }
        }

        return await next(context);
    }
}
```

### Підключення до маршруту
```csharp
validateGroup.MapPost("/", Results<Ok<string>, ValidationProblem> (ProductInput input, ICatalog catalog) =>
{
    // Тіло методу викликається лише якщо валідація успішна
    return TypedResults.Ok($"Товар прийнято: {input.Name}");
})
.AddEndpointFilter<ValidationFilter<ProductInput>>();
```

## Як запустити і перевірити

### Запуск проєкту
```bash
dotnet run --project src/11.MinimalApi.BindingAndValidation
```
Порт: `5111`.

### Тестові сценарії

1. **Прив'язка кількох параметрів через `[AsParameters]`:**
   ```http
   GET http://localhost:5111/bind/search/3?term=macbook&pageSize=10
   ```
   cURL:
   ```bash
   curl -s "http://localhost:5111/bind/search/3?term=macbook&pageSize=10"
   ```
   Повертає структурований JSON з розпарсеними полями.

2. **Успішна валідація:**
   ```http
   POST http://localhost:5111/validate
   Content-Type: application/json

   {
     "name": "Ноутбук Dell XPS",
     "price": 1450.00,
     "categoryId": 1
   }
   ```
   cURL:
   ```bash
   curl -s -X POST http://localhost:5111/validate -H "Content-Type: application/json" -d "{\"name\":\"Ноутбук Dell XPS\",\"price\":1450.00,\"categoryId\":1}"
   ```
   Повертає `200 OK`.

3. **Перехоплення невалідної моделі фільтром (400 ValidationProblem):**
   ```http
   POST http://localhost:5111/validate
   Content-Type: application/json

   {
     "name": "x",
     "price": -5,
     "categoryId": 0
   }
   ```
   cURL:
   ```bash
   curl -s -X POST http://localhost:5111/validate -H "Content-Type: application/json" -d "{\"name\":\"x\",\"price\":-5,\"categoryId\":0}"
   ```
   Повертає `400 Bad Request` у форматі RFC 9457 `ValidationProblemDetails`.

## Питання для самоперевірки та співбесіди

1. **Чому Minimal APIs не валідують моделі за замовчуванням так само, як MVC-контролери?**
   *Відповідь:* У MVC-контролерах за це відповідає атрибут `[ApiController]`, який запускає важкий фільтр моделі. Minimal APIs спроєктовані для максимальної швидкодії без зайвих накладних витрат. Розробник сам вирішує, яку бібліотеку використовувати для перевірки (DataAnnotations або FluentValidation) за допомогою `IEndpointFilter`.
2. **Яка різниця між Middleware та `IEndpointFilter`?**
   *Відповідь:* Middleware виконується для абсолютно всіх запитів на рівні конвеєра HTTP до того, як вибрано конкретний кінцевий маршрут, і працює лише з сирим `HttpContext`. `IEndpointFilter` виконується на рівні обраного ендпоінта і має прямий типізований доступ до розпарсених аргументів методу (`context.Arguments`).
3. **Для чого потрібен атрибут `[AsParameters]`?**
   *Відповідь:* Він групує параметри з різних джерел (route, query string, headers, DI services) в єдиний об'єкт або рекорд, уникаючи довгих сигнатур у хендлерах Minimal API.

---

## Підсумки
- `[AsParameters]` спрощує сигнатури маршрутів і дозволяє повторно використовувати DTO для пошуку й пагінації.
- `Endpoint Filters` — це потужний інструмент створення конвеєра обробки на рівні окремих ендпоінтів у Minimal APIs, що є прямою альтернативою MVC Action Filters.
