# 14. REST: Ресурси та HTTP-дієслова (14.Rest.ResourcesAndVerbs)

## Призначення та огляд

Цей проєкт розпочинає модуль «REST по-справжньому». Багато розробників помилково називають будь-який JSON API через HTTP словом «REST». Проте справжній REST (Representational State Transfer) — це архітектурний стиль, що базується на суворих семантичних принципах стандарту **RFC 9110 (HTTP Semantics)**:
1. Орієнтація на **Ресурси (Resources)**, а не на RPC-процедури;
2. Коректне використання **HTTP-методів** (дієслів);
3. Дотримання властивостей **Safe** (безпечність) та **Idempotent** (ідемпотентність);
4. Точні коди відповідей та наявність заголовка `Location`.

---

## Властивості HTTP-методів

| Метод | Безпечний (Safe)? | Ідемпотентний (Idempotent)? | Семантика в REST | Стандартні коди успіху |
|---|:---:|:---:|---|---|
| **`GET`** | ✅ Так | ✅ Так | Читання ресурсу або колекції. **Ніколи не змінює стан** сервера! | 200 OK |
| **`HEAD`** | ✅ Так | ✅ Так | Те саме, що GET, але повертає лише заголовки без тіла. | 200 OK |
| **`POST`** | ❌ Ні | ❌ Ні | Створення під-ресурсу в колекції або виконання операції над ресурсом. Повторний виклик створить дублікат! | 201 Created |
| **`PUT`** | ❌ Ні | ✅ Так | **Повна заміна** ресурсу за вказаним URI. Повторний виклик залишає той самий стан. | 200 OK / 204 No Content |
| **`DELETE`**| ❌ Ні | ✅ Так | Видалення ресурсу. Повторне видалення залишає систему в стані "ресурс видалено". | 204 No Content |
| **`PATCH`** | ❌ Ні | ❌ Ні | Часткове оновлення (delta). Не гарантує ідемпотентності за замовчуванням. | 200 OK / 204 No Content |

> [!NOTE]
> **Safe (Безпечний):** Виклик методу не призводить до зміни стану ресурсу на сервері. Клієнти, пошукові боти та браузери можуть викликати `GET` без побоювання стерти чи змінити дані.
>
> **Idempotent (Ідемпотентний):** Скільки б разів поспіль клієнт не виконав один і той самий запит (`N >= 1`), підсумковий стан сервера буде ідентичним результату одного виклику. При збоях мережі клієнт може безпечно повторювати (`retry`) запити `PUT` і `DELETE`.

## Дизайн URI: Ресурси замість дій

### ❌ Поганий дизайн (RPC-style):
- `POST /getProducts`
- `POST /api/createProduct`
- `GET /api/deleteProduct?id=5`
- `POST /api/updateProductPrice`

### ✅ Правильний дизайн (RESTful):
- `GET /products` — отримати колекцію товарів
- `GET /products/5` — отримати конкретний товар
- `POST /products` — створити товар у колекції
- `PUT /products/5` — повністю замінити товар №5
- `DELETE /products/5` — видалити товар №5

Іменники у множині позначають ресурси, а дію над ними визначає **метод HTTP**.

## Розбір коду: `ProductsController`

```csharp
[ApiController]
[Route("products")]
public sealed class ProductsController(ICatalog catalog) : ControllerBase
{
    // GET колекція → завжди 200 (навіть якщо список порожній)
    [HttpGet]
    public IEnumerable<Product> GetAll() => catalog.GetProducts();

    // GET елемент → 200 або 404
    [HttpGet("{id:int}")]
    public ActionResult<Product> GetById(int id)
        => catalog.FindProduct(id) is { } p ? p : NotFound();

    // POST → 201 Created + Location. НЕ ідемпотентний.
    [HttpPost]
    public ActionResult<Product> Create(ProductInput input)
    {
        if (catalog.FindCategory(input.CategoryId) is null)
            return BadRequest("Категорії з таким Id немає.");

        var created = catalog.Add(input);
        return CreatedAtAction(nameof(GetById), new { id = created.Id }, created);
    }

    // PUT → повна заміна. Ідемпотентний.
    [HttpPut("{id:int}")]
    public ActionResult<Product> Replace(int id, ProductInput input)
        => catalog.Replace(id, input) is { } updated ? updated : NotFound();

    // DELETE → 204. Ідемпотентний: видалення вже видаленого повертає 204!
    [HttpDelete("{id:int}")]
    public IActionResult Delete(int id)
    {
        catalog.Delete(id);
        return NoContent();
    }
}
```

## Як запустити і перевірити

### Запуск проєкту
```bash
dotnet run --project src/14.Rest.ResourcesAndVerbs
```
Порт: `5014`.

### Тестові сценарії

1. **Читання колекції (Safe, Idempotent):**
   ```http
   GET http://localhost:5014/products
   ```

2. **Створення ресурсу (Unsafe, Non-idempotent):**
   ```http
   POST http://localhost:5014/products
   Content-Type: application/json

   {
     "name": "IPS Монітор 27\"",
     "price": 299.99,
     "categoryId": 2
   }
   ```
   Зверніть увагу на статус `201` і заголовок `Location`.

3. **Перевірка ідемпотентності DELETE:**
   ```http
   DELETE http://localhost:5014/products/2
   ```
   - Перший виклик повертає `204 No Content`.
   - Повторний виклик того ж `DELETE` повертає **знову `204 No Content`**! Сервер не падає з помилкою 500, адже ресурс гарантовано відсутній.

## Підсумки
- REST базується на семантиці HTTP, а не винаходить власні протоколи поверх POST.
- Розуміння ідемпотентності дозволяє правильно проєктувати повторні спроби клієнтів (retry logic) у мікросервісних архітектурах.
