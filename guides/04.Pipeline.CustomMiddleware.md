# 04. Власні Middleware у вигляді класів (04.Pipeline.CustomMiddleware)

## Призначення та огляд

Коли логіка middleware розростається, її виділяють в окремі тестовані класи. ASP.NET Core підтримує два різні підходи до написання middleware-класів:
1. **Convention-based (за конвенцією)** — звичайний C#-клас із конструктором, що приймає `RequestDelegate next`, і методом `InvokeAsync(HttpContext)`.
2. **Factory-based (на основі інтерфейсу `IMiddleware`)** — строга типізація через інтерфейс, що дозволяє інжектувати `Scoped`-залежності прямо в конструктор.

У цьому проєкті демонструються обидва підходи на прикладі `RequestTimingMiddleware` (вимірювання швидкодії) та `CorrelationIdMiddleware` (наскрізний ідентифікатор запиту).

---

## Порівняння двох підходів

| Критерій | Convention-based (`RequestTimingMiddleware`) | `IMiddleware` (`CorrelationIdMiddleware`) |
|---|---|---|
| **Реалізація інтерфейсу** | Немає (довільний клас) | Реалізує `IMiddleware` |
| **Життєвий цикл** | **Singleton** (створюється один раз при старті) | **Scoped** або Transient (контролюється DI) |
| **Реєстрація в DI** | Не обов'язкова | **Обов'язкова**: `builder.Services.AddScoped<T>()` |
| **Впровадження залежностей** | У конструктор — лише Singleton; Scoped — як параметри методу `InvokeAsync(HttpContext, IMyService)` | У конструктор можна впроваджувати Scoped-сервіси |
| **Швидкодія** | Максимальна (прямий виклик через делегат) | Незначний оверхед на фабрику `IMiddlewareFactory` |

## Розбір коду

### 1. Convention-based: `RequestTimingMiddleware`
```csharp
public sealed class RequestTimingMiddleware(RequestDelegate next, ILogger<RequestTimingMiddleware> logger)
{
    public async Task InvokeAsync(HttpContext context)
    {
        var sw = Stopwatch.StartNew();
        await next(context);
        sw.Stop();

        logger.LogInformation("Час виконання: {ElapsedMs} мс", sw.ElapsedMilliseconds);
    }
}
```
Зверніть увагу: `next` приходить один раз у конструктор під час ініціалізації конвеєра.

### 2. `IMiddleware`: `CorrelationIdMiddleware`
```csharp
public sealed class CorrelationIdMiddleware : IMiddleware
{
    private const string HeaderName = "X-Correlation-ID";

    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        // Читаємо наявний ідентифікатор від клієнта або генеруємо новий
        var correlationId = context.Request.Headers[HeaderName].FirstOrDefault()
            ?? Guid.NewGuid().ToString("N");

        context.Items["CorrelationId"] = correlationId;
        context.Response.Headers[HeaderName] = correlationId;

        await next(context);
    }
}
```
Тут `next` передається аргументом у метод `InvokeAsync`, а сам клас реєструється в DI:
```csharp
builder.Services.AddScoped<CorrelationIdMiddleware>();
```

### 3. Extension-методи для зручного підключення
Замість сирого `app.UseMiddleware<RequestTimingMiddleware>()`, створюють читабельні методи розширення:
```csharp
public static class MiddlewareExtensions
{
    public static IApplicationBuilder UseRequestTiming(this IApplicationBuilder app)
        => app.UseMiddleware<RequestTimingMiddleware>();

    public static IApplicationBuilder UseCorrelationId(this IApplicationBuilder app)
        => app.UseMiddleware<CorrelationIdMiddleware>();
}
```

У `Program.cs` це виглядає лаконічно й знайомо:
```csharp
app.UseCorrelationId();
app.UseRequestTiming();
```

## Як запустити і перевірити

### Запуск проєкту
```bash
dotnet run --project src/04.Pipeline.CustomMiddleware
```
Порт: `5004`.

### Перевірка запиту

#### 1. Без передачі X-Correlation-ID (сервер генерує новий)
```http
GET http://localhost:5004/
```
У відповіді:
- Тіло містить згенерований `correlationId`.
- У заголовках відповіді повертаються `X-Correlation-ID` та `X-Powered-By`.

#### 2. З клієнтським кореляційним ID
```http
GET http://localhost:5004/
X-Correlation-ID: my-custom-trace-12345
```
Відповідь:
```json
{
  "message": "Дивіться заголовки відповіді: X-Correlation-ID, X-Powered-By.",
  "correlationId": "my-custom-trace-12345"
}
```
Сервер підхопив наявний ID і зберіг його для наскрізного трасування (Distributed Tracing).

## Підсумки
- Якщо middleware не потребує Scoped-сервісів у конструкторі — обирайте **Convention-based** (він легший і швидший).
- Якщо middleware залежить від Scoped-сервісів (наприклад `DbContext` чи поточного користувача) — обирайте **`IMiddleware`**.
- Завжди ховайте `app.UseMiddleware<T>()` за виразними методами розширення `app.UseXxx()`.
