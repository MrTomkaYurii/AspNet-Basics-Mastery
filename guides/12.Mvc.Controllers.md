# 12. Глибокий розбір контролерів MVC (12.Mvc.Controllers)

## Призначення та огляд

Цей проєкт присвячений детальному розгляду того, як влаштований механізм контролерів для Web API у ASP.NET Core:
1. Що конкретно вмикає атрибут **`[ApiController]`**;
2. Як працює повернення результатів через **`ActionResult<T>`**;
3. Як налаштувати маршрутизацію через префікс API (`/api/products`);
4. Чому контролери залишаються популярним вибором для великих enterprise-систем із сотнями операцій над сутностями.

---

## Що насправді робить атрибут `[ApiController]`

Атрибут `[ApiController]` — це не просто маркер для документації. Він змінює поведінку контролера за кількома ключовими напрямками:

1. **Вимога атрибутної маршрутизації (Attribute Routing):**
   Дії контролера обов'язково повинні мати явні маршрути (`[Route]`, `[HttpGet]`). Контролер не може використовувати застарілу конвенційну маршрутизацію виду `{controller}/{action}/{id}`.
2. **Автоматична відповідь 400 (Automatic HTTP 400 Responses):**
   Якщо `ModelState.IsValid == false`, фреймворк автоматично перериває дію і повертає `400 ValidationProblemDetails`. Вам не потрібно писати `if (!ModelState.IsValid) return BadRequest();` у кожному методі.
3. **Вивід джерела прив'язки (Binding Source Parameter Inference):**
   Платформа автоматично здогадується, звідки брати параметри:
   - Складні об'єкти автоматично вважаються `[FromBody]`;
   - Прості типи вважаються `[FromQuery]`;
   - Назви, що збігаються з сегментами маршруту, автоматично беруться `[FromRoute]`.
4. **Формат Problem Details для статус-кодів помилок:**
   Всі виклики методів `BadRequest()`, `NotFound()` тощо повертають об'єкти згідно зі стандартом RFC 9457 `ProblemDetails`.

## Особливості повернення результатів: `ActionResult<T>`

ASP.NET Core дозволяє три типи повернення з дій контролера:

| Тип повернення | Приклад | Особливості |
|---|---|---|
| **Конкретний тип `T`** | `public Product Get()` | Найпростіший, але не дозволяє повернути `NotFound()` або `BadRequest()`. |
| **`IActionResult`** | `public IActionResult Get()` | Повний контроль над статусом, але втрачається інформація про тип тіла для документації Swagger. |
| **`ActionResult<T>`** | `public ActionResult<Product> Get()` | **Золота середина:** дозволяє повернути як `Product` напряму (автоматично стає 200 OK), так і будь-який `ActionResult` (`NotFound()`, `Forbid()`). OpenAPI автоматично фіксує схему типу `T` для коду 200. |

## Розбір коду

```csharp
[ApiController]
[Route("api/[controller]")] // [controller] динамічно підставляє "products"
public sealed class ProductsController(ICatalog catalog) : ControllerBase
{
    [HttpGet("{id:int}")]
    public ActionResult<Product> GetById(int id)
    {
        var product = catalog.FindProduct(id);
        if (product is null)
            return NotFound(); // Повертає 404 ProblemDetails

        return product; // Автоматично загортається в 200 OK з типізацією Product
    }
}
```

## Як запустити і перевірити

### Запуск проєкту
```bash
dotnet run --project src/12.Mvc.Controllers
```
Порт: `5012`.

### Тестові сценарії

1. **Отримання товару (успіх 200 з типом Product):**
   ```http
   GET http://localhost:5012/api/products/1
   ```
   cURL:
   ```bash
   curl -s http://localhost:5012/api/products/1
   ```

2. **Неіснуючий товар (404 ProblemDetails):**
   ```http
   GET http://localhost:5012/api/products/999
   ```
   cURL:
   ```bash
   curl -s -i http://localhost:5012/api/products/999
   ```
   Відповідь:
   ```json
   {
     "type": "https://tools.ietf.org/html/rfc9110#section-15.5.5",
     "title": "Not Found",
     "status": 404
   }
   ```

3. **Створення з авто-400:**
   ```http
   POST http://localhost:5012/api/products
   Content-Type: application/json

   {
     "name": "",
     "price": -1
   }
   ```
   cURL:
   ```bash
   curl -s -i -X POST http://localhost:5012/api/products -H "Content-Type: application/json" -d "{\"name\":\"\",\"price\":-1}"
   ```
   Повертає стандартизований `400 ValidationProblemDetails`.

## Питання для самоперевірки та співбесіди

1. **Як працює життєвий цикл контролера в ASP.NET Core під час HTTP-запиту?**
   *Відповідь:* Екземпляр контролера створюється фабрикою контролерів заново для **кожного HTTP-запиту** (фактично `Transient` або `Scoped`). Після відпрацювання дії та формування результату викликом `Dispose()` контролер знищується. Тому контролери не повинні зберігати міжзапитовий стан у звичайних полях.
2. **Як інжектувати залежність тільки в один конкретний метод дії, щоб не перевантажувати конструктор?**
   *Відповідь:* За допомогою атрибута `[FromServices] MyService service` у списку параметрів потрібного методу дії (Action).
3. **Чи можна вимкнути автоматичну перевірку моделі при збереженні атрибута `[ApiController]`?**
   *Відповідь:* Так, встановивши опцію `options.SuppressModelStateInvalidFilter = true` у виклику `builder.Services.Configure<ApiBehaviorOptions>(...)`. Це буває потрібно, якщо ви хочете кастомізувати логіку перевірки вручну в контролері.

---

## Підсумки
- Атрибут `[ApiController]` стандартизує поведінку контролерів для Web API.
- `ActionResult<T>` забезпечує строгу типізацію для клієнтів і генераторів коду (OpenAPI / Swagger / NSwag).
