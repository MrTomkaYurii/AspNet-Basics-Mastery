# 02. Сервери та середовища виконання (02.Hosting.ServersAndEnvironment)

## Призначення та огляд

Цей приклад висвітлює дві важливі концепції хостингу:
1. **HTTP-сервер Kestrel** — конфігурація мережевих обмежень (заголовки, розмір тіла запиту, таймаути).
2. **Середовища виконання (Environments)** — як застосунок розрізняє `Development` та `Production`, як середовище впливає на конвеєр обробки помилок і як файли конфігурації автоматично перекривають значення залежно від оточення.

---

## Архітектура та ключові механізми

### 1. HTTP-сервери в екосистемі ASP.NET Core
- **Kestrel**: Швидкий крос-платформний веб-сервер, написаний на C#. Може працювати як self-hosted (напряму дивитися в інтернет) або позаду reverse proxy (Nginx, YARP, Envoy, Cloudflare).
- **IIS (Windows)**: Працює в in-process (код виконується у `w3wp.exe`) або out-of-process (IIS пересилає запити до Kestrel).
- **HTTP.sys (Windows)**: Kernel-mode сервер Windows для сценаріїв із Windows-автентифікацією чи port-sharing.

### 2. Конфігурація Kestrel у коді
```csharp
builder.WebHost.ConfigureKestrel(options =>
{
    options.AddServerHeader = false;                      // Приховуємо заголовок "Server: Kestrel" для безпеки
    options.Limits.MaxRequestBodySize = 1 * 1024 * 1024;  // Ліміт тіла запиту: 1 МБ
});
```

### 3. Середовища виконання (`IWebHostEnvironment`)
Середовище визначається змінною `ASPNETCORE_ENVIRONMENT`.
Стандартні конвенції:
- **`Development`**: Вмикається детальна сторінка помилок (`app.UseDeveloperExceptionPage()`), доступні діагностичні ендпоінти, гаряче перезавантаження, документація OpenAPI.
- **`Production`**: Заборонено виводити стектрейси клієнтам! Використовується `app.UseExceptionHandler("/error")` із поверненням узагальненого Problem Details (RFC 9457).

### 4. Ієрархія налаштувань (`Configuration hierarchy`)
Файли конфігурації читаються послідовно:
1. `appsettings.json` (базові налаштування)
2. `appsettings.{Environment}.json` (перекривають базові для конкретного середовища)
3. Змінні середовища системи (мають вищий пріоритет)
4. Аргументи командного рядка (найвищий пріоритет)

У прикладі:
- `appsettings.json`: `"ExperimentalSearch": true`
- `appsettings.Production.json`: `"ExperimentalSearch": false`

## Як запустити і перевірити

### Запуск у режимі Development (типовий)
```bash
dotnet run --project src/02.Hosting.ServersAndEnvironment
```
Порт: `5002`.

#### Запити:
1. **Перевірка поточного середовища:**
   ```http
   GET http://localhost:5002/env
   ```
   Повертає `EnvironmentName: "Development"`, `IsDevelopment: true`.

2. **Діагностика сервера:**
   ```http
   GET http://localhost:5002/server
   ```
   Повертає ім'я сервера (`KestrelServer`) та список адрес, які він слухає.

3. **Перевірка перекриття конфігурації:**
   ```http
   GET http://localhost:5002/config
   ```
   Повертає `ExperimentalSearch: true` (значення з `appsettings.json`).

4. **Ендпоінт, доступний лише в Development:**
   ```http
   GET http://localhost:5002/dev/ping
   ```
   Повертає `"pong (тільки в Development)"`.

---

### Запуск у режимі Production
Виконайте в терміналі:
```bash
dotnet run --project src/02.Hosting.ServersAndEnvironment --environment Production
```
Тепер:
- `GET /config` поверне `ExperimentalSearch: false` (перекрито `appsettings.Production.json`).
- `GET /dev/ping` поверне `404 Not Found`, оскільки маршрут узагалі не реєструвався в конвеєрі.

---

## Підсумки та безпека
- Ніколи не вмикайте `UseDeveloperExceptionPage()` у середовищі Production, щоб уникнути витоку конфіденційної інформації (паролі, рядки підключення, внутрішня структура класів у стек-трейсі).
- Приховування заголовка сервера (`AddServerHeader = false`) ускладнює автоматизоване сканування версії сервера зловмисниками.
