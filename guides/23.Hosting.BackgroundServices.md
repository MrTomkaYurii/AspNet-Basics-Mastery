# 23. Фонові задачі та Hosted Services (23.Hosting.BackgroundServices)

## Призначення та огляд

У веб-застосунках багато важливих задач мають виконуватися у фоновому режимі (asynchronous background processing), щоб не блокувати користувача, який очікує швидку відповідь по HTTP:
- Надсилання email та push-повідомлень;
- Обробка важких звітів та відеофайлів;
- Періодична синхронізація залишків або очищення застарілих кешів;
- Вичитування повідомлень із брокерів (RabbitMQ, Kafka, Azure Service Bus).

Цей проєкт демонструє сучасні інструменти фонової роботи в .NET 10:
1. Базовий клас **`BackgroundService`**;
2. Сучасний інтервальний таймер **`PeriodicTimer`**;
3. Внутрішню чергу задач на **`System.Threading.Channels`**;
4. **Вирішення проблеми Captive Dependency**: як безпечно використовувати `Scoped`-сервіси у довгоживучому `Singleton`-воркері через `IServiceScopeFactory`.

---

## Пастка Captive Dependency у фонових сервісах

Будь-який `BackgroundService` реєструється в DI як **Singleton** — він стартує разом із застосунком і живе до його зупинки.

### ❌ Помилка:
```csharp
// ПОМИЛКА: Scoped-сервіс у конструкторі Singleton-воркера!
public class BadWorker(ICatalog catalog) : BackgroundService
```
Якщо спробувати так зробити:
1. У Development фреймворк викине виняток під час старту застосунку (перевірка валідації областей).
2. Якщо валідація вимкнена, екземпляр `ICatalog` (або `DbContext`) ніколи не буде звільнений, накопичуватиме кеш у пам'яті та призведе до витоку ресурсів або стану перегонів між потоками.

### ✅ Правильне рішення через `IServiceScopeFactory`:
```csharp
public class GoodWorker(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            // Створюємо власну ізольовану область під кожну ітерацію або задачу:
            using var scope = scopeFactory.CreateScope();
            var catalog = scope.ServiceProvider.GetRequiredService<ICatalog>();

            catalog.DoSomething(); // Чисто, ізольовано, ресурси звільняються відразу після виходу з using
        }
    }
}
```

## Використання `PeriodicTimer` у .NET

Замість застарілих `System.Threading.Timer` або `while(true) { await Task.Delay(); }`, у сучасному .NET використовується `PeriodicTimer`:
```csharp
using var timer = new PeriodicTimer(TimeSpan.FromSeconds(10));

while (!stoppingToken.IsCancellationRequested &&
       await timer.WaitForNextTickAsync(stoppingToken))
{
    // Виконується строго кожні 10 секунд без дрейфу часу
}
```
Він автоматично зупиняється при скасуванні токена `stoppingToken` і гарантує, що наступний такт не накладеться на попередній, якщо ітерація зайняла більше часу.

## Асинхронні черги на `System.Threading.Channels`

У проєкті реалізовано внутрішню чергу `BackgroundTaskQueue`:
- Ендпоінт `POST /queue/job` кладе задачу в канал:
  ```csharp
  await queue.EnqueueAsync("Генерація-звіту");
  return Results.Accepted(...); // 202 Accepted
  ```
- Воркер вичитує задачі в неблокуючому асинхронному потоці:
  ```csharp
  await foreach (var taskName in queue.ReadAllAsync(stoppingToken))
  {
      // Обробка кожної задачі
  }
  ```

## Як запустити і перевірити

### Запуск проєкту
```bash
dotnet run --project src/23.Hosting.BackgroundServices
```
Порт: `5023`.

### Тестові сценарії

1. **Спостереження за періодичним воркером:**
   Подивіться в термінал. Кожні 10 секунд з'являється лог:
   ```
   info: Hosting.BackgroundServices.PeriodicCatalogAuditService[0]
         [Аудит каталогу] Періодична перевірка: доступно 3 активних товарів.
   ```

2. **Постановка задачі в чергу (202 Accepted):**
   ```http
   POST http://localhost:5023/queue/job?name=Експорт_товарів_у_CSV
   ```
   cURL:
   ```bash
   curl -s -X POST "http://localhost:5023/queue/job?name=Export_CSV"
   ```
   Відповідь повертається миттєво:
   ```json
   {
     "message": "Задачу успішно поставлено в чергу на обробку",
     "task": "Export_CSV"
   }
   ```
   У консолі сервера з'являється запис воркера:
   ```
   info: Hosting.BackgroundServices.QueuedTaskProcessor[0]
         Обробка фонової задачі 'Export_CSV': зараз у каталозі 3 товарів
   ```

3. **Коректне завершення (Graceful Shutdown):**
   Натисніть `Ctrl+C`. Обидва воркери отримують сигнал через `stoppingToken` і коректно завершують поточну роботу без втрати стану.

## Питання для самоперевірки та співбесіди

1. **Чому не можна інжектити `DbContext` або інший `Scoped`-сервіс напряму в конструктор `BackgroundService`?**
   *Відповідь:* `BackgroundService` є довгоживучим Singleton-об'єктом. Інжектування `Scoped`-сервісу призведе до Captive Dependency: сервіс ніколи не знищиться, його внутрішній стан і кеші зростатимуть (витік пам'яті), а доступ до нього з різних фонових ітерацій спричинить конфлікти потоків.
2. **Які переваги має `PeriodicTimer` порівняно зі старим `System.Threading.Timer` або `Task.Delay`?**
   *Відповідь:* `PeriodicTimer` не дрейфує в часі, є повністю асинхронним (`await timer.WaitForNextTickAsync(ct)`), безпечно інтегрується з `CancellationToken`, не допускає перекриття викликів (overlap) і не породжує складних потокових колізій, характерних для callback-ів `Timer`.
3. **Чому для внутрішньої черги краще використовувати `System.Threading.Channels`, а не `ConcurrentQueue`?**
   *Відповідь:* `ConcurrentQueue` вимагає активного опитування (polling у циклі з `Task.Delay`), що марнує процесорний час або додає затримку. `Channels` надають реактивну неблокуючу модель продюсер-споживач (через `await channel.Reader.WaitToReadAsync()` або `ReadAllAsync()`), підтримують обмеження місткості (backpressure) та чисте асинхронне завершення.

---

## Підсумки
- `BackgroundService` дозволяє організувати надійну фонову обробку прямо всередині вашого веб-процесу без необхідності розгортання окремих консольних воркерів на ранніх етапах проєкту.
- `System.Threading.Channels` забезпечує потокобезпечну, швидку та ефективну за пам'яттю взаємодію між веб-запитами та фоновими потоками.
