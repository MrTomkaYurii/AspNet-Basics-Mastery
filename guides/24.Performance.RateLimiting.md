# 24. Обмеження частоти запитів: Rate Limiting (24.Performance.RateLimiting)

## Призначення та огляд

Захист веб-сервісів від зловживань, brute-force атак, скрапінгу даних та випадкового перевантаження від збійних клієнтів є обов'язковою вимогою сучасної архітектури API.

У платформі ASP.NET Core починаючи з .NET 7/8 та вдосконалено в .NET 10 доступна високопродуктивна вбудована підсистема **Rate Limiting** (`Microsoft.AspNetCore.RateLimiting` на основі `System.Threading.RateLimiting`).

Цей приклад розкриває:
1. Алгоритми обмеження: **Fixed Window**, **Sliding Window**, **Token Bucket**;
2. Налаштування політик та їх призначення на ендпоінти через `.RequireRateLimiting("назва")`;
3. Вимкнення лімітів для окремих публічних ендпоінтів через `.DisableRateLimiting()`;
4. Коректну обробку відхилених запитів (`OnRejected`) згідно зі стандартом **RFC 6585**: код `429 Too Many Requests` та заголовок `Retry-After`.

---

## Порівняння алгоритмів Rate Limiting

| Алгоритм | Принцип дії | Переваги | Коли використовувати |
|---|---|---|---|
| **Fixed Window (Фіксоване вікно)** | Лічильник скидається кожні $N$ секунд (наприклад, 100 запитів на хвилину). | Мінімальне споживання пам'яті, простий у конфігурації. | Загальний захист від перевантаження звичайних API. |
| **Sliding Window (Ковзне вікно)** | Вікно розбивається на під-сегменти, враховуючи активність на межі вікон. | Захищає від граничних сплесків на стику хвилин. | Важливі публічні API з рівномірним навантаженням. |
| **Token Bucket (Кошик маркерів)** | Є кошик певної місткості, який поповнюється маркерами з фіксованою швидкістю. Кожен запит витрачає 1 маркер. | Дозволяє короткочасні сплески трафіку (bursts) за наявності невитрачених маркерів. | API для мобільних застосунків або інтеграцій, де клієнт робить пачку запитів при старті. |
| **Concurrency Limiter (Обмежувач одночасності)** | Контролює кількість одночасно оброблюваних запитів. | Захищає від вичерпання пулу потоків та пам'яті. | Важкі розрахункові ендпоінти, експорт великих звітів. |

## Розбір коду

### 1. Налаштування підсистеми у `Program.cs`
```csharp
builder.Services.AddRateLimiter(options =>
{
    // Обробник перевищення ліміту (429 + Retry-After)
    options.OnRejected = async (context, ct) =>
    {
        context.HttpContext.Response.StatusCode = StatusCodes.Status429TooManyRequests;

        if (context.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retryAfter))
        {
            context.HttpContext.Response.Headers.RetryAfter = ((int)retryAfter.TotalSeconds).ToString();
        }

        await context.HttpContext.Response.WriteAsJsonAsync(new
        {
            title = "Забагато запитів (Too Many Requests)",
            status = 429,
            detail = "Ви перевищили встановлений ліміт запитів. Спробуйте пізніше.",
            retryAfterSeconds = (int)retryAfter.TotalSeconds
        }, ct);
    };

    // Політика Fixed Window: максимум 3 запити за 10 секунд
    options.AddFixedWindowLimiter("fixed", opt =>
    {
        opt.PermitLimit = 3;
        opt.Window = TimeSpan.FromSeconds(10);
        opt.QueueLimit = 0; // без черги — відхиляти миттєво
    });

    // Політика Token Bucket: місткість 5, поповнення на 1 кожні 3 секунди
    options.AddTokenBucketLimiter("token_bucket", opt =>
    {
        opt.TokenLimit = 5;
        opt.ReplenishmentPeriod = TimeSpan.FromSeconds(3);
        opt.TokensPerPeriod = 1;
        opt.AutoReplenishment = true;
    });
});
```

### 2. Підключення middleware
```csharp
app.UseRateLimiter(); // Важливо: після UseRouting() і до ендпоінтів!
```

### 3. Застосування до маршрутів
```csharp
// Захищено політикою "fixed"
app.MapGet("/api/fixed", () => Results.Ok(new { message = "Успіх" }))
   .RequireRateLimiting("fixed");

// Відкрито без лімітів
app.MapGet("/api/unlimited", () => Results.Ok(new { message = "Без обмежень" }))
   .DisableRateLimiting();
```

## Як запустити і перевірити

### Запуск проєкту
```bash
dotnet run --project src/24.Performance.RateLimiting
```
Порт: `5024`.

### Тестові сценарії

1. **Нормальне виконання запитів (перші 3):**
   ```http
   GET http://localhost:5024/api/fixed
   ```
   cURL:
   ```bash
   curl -s http://localhost:5024/api/fixed
   ```
   Повертає `200 OK`.

2. **Перевищення ліміту (4-й запит протягом 10 секунд):**
   ```http
   GET http://localhost:5024/api/fixed
   ```
   Перевірка швидким циклом у Bash / PowerShell:
   ```bash
   # Відправити 5 швидких запитів підряд
   for i in {1..5}; do curl -s -i http://localhost:5024/api/fixed | grep -E "(HTTP/|retryAfter)"; done
   ```
   Сервер повертає **`429 Too Many Requests`**:
   ```json
   {
     "title": "Забагато запитів (Too Many Requests)",
     "status": 429,
     "detail": "Ви перевищили встановлений ліміт запитів. Спробуйте пізніше.",
     "retryAfterSeconds": 7
   }
   ```
   У заголовках повертається стандартний HTTP-заголовок: `Retry-After: 7`.

3. **Сплеск запитів у Token Bucket:**
   Швидко надішліть 5 запитів на `GET http://localhost:5024/api/token` — усі 5 пройдуть завдяки місткості кошика (bucket capacity). 6-й запит отримає 429 до моменту нарахування наступного токена.

## Питання для самоперевірки та співбесіди

1. **Чому для Rate Limiting використовується саме статус `429 Too Many Requests`, а не `403 Forbidden`?**
   *Відповідь:* `403 Forbidden` означає, що клієнту взагалі заборонено доступ до ресурсу (відсутні права, і повторювати запит без зміни прав безглуздо). `429 Too Many Requests` вказує на тимчасове перевищення ліміту частоти і супроводжується заголовком `Retry-After`, що вказує клієнту точний час очікування.
2. **У чому ключова відмінність між алгоритмами Fixed Window та Sliding Window?**
   *Відповідь:* У Fixed Window можливий граничний сплеск (traffic burst on window boundaries): якщо ліміт 100/хв, клієнт може надіслати 100 запитів на 59-й секунді і ще 100 на 1-й секунді наступної хвилини (200 запитів за 2 секунди!). Sliding Window розбиває вікно на менші інтервали і плавно розраховує середнє ковзне навантаження, усуваючи цю вразливість.
3. **Коли доцільно обирати Token Bucket?**
   *Відповідь:* Коли клієнтам дозволено робити короткочасні сплески активності (наприклад, мобільний застосунок робить 5 паралельних запитів для завантаження головного екрана), але середня швидкість споживання API повинна залишатися стабільною.

---

## Підсумки
- Вбудований Rate Limiter у .NET працює на рівні пам'яті процесу з мінімальним оверхедом і не вимагає сторонніх Nuget-пакетів.
- Заголовок `Retry-After` допомагає коректним клієнтам та фронтенду автоматично виставити паузу перед повторною спробою.
